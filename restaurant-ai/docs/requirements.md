# Requirements

## 1. Project Goal

餐廳每月需要進行食材庫存盤點，過程需要整理食材進貨、出餐及庫存異動資料，若依賴人工計算，不僅耗費時間，也需要熟悉餐廳庫存計算方式。

因此，本專案希望建立一套餐廳庫存管理系統，將食材、餐點與食材使用比例建立關聯，並透過進貨（IN）與出餐扣料（OUT）紀錄計算目前庫存，降低人工盤點與計算的負擔。

系統進一步設定各食材的最低庫存量，根據歷史使用量計算平均每日使用量、預測需求量及建議補貨量，協助使用者判斷後續所需的補貨數量，降低新人因不熟悉庫存計算方式而產生錯誤的情況。

原先規劃使用 AI 分析歷史資料並進行庫存預測，但實作後將庫存預測與補貨計算改由後端程式依照明確的 Business Rules 執行，以確保計算結果具有一致性與可預期性。

AI 則應用於「AI 庫存助理」，讓使用者可以透過自然語言詢問目前庫存、低庫存食材、庫存預測及補貨資訊，AI 再透過後端 Tools 取得實際資料後產生回覆。

## 2. User Roles

本系統主要使用者為餐廳內部人員，依照工作職責與資料管理需求分為 Admin 與 User 兩種角色。

### 2.1 Admin（主管級）

Admin 具備完整的庫存與餐點管理權限，可執行以下功能：

- 查看目前庫存
- 庫存管理
  - 新增、修改、刪除食材
  - Excel 匯入
  - 記錄進貨與出貨
- 查看歷史庫存記錄
- 使用庫存預測功能
- 餐點管理
  - 出餐
  - 新增餐點
  - 修改餐點
  - 刪除餐點
  - 查看餐點及食材比例
- 使用 AI 庫存助理

### 2.2 User（一般員工）

User 主要負責日常庫存查詢與餐點操作，具備以下功能：

- 查看目前庫存
- 查看庫存預測
- 餐點操作
  - 出餐
  - 查看餐點及食材比例
- 使用 AI 庫存助理

User 不具備以下管理權限：

- 新增、修改或刪除食材
- Excel 匯入
- 查看歷史庫存記錄
- 新增、修改或刪除餐點

## 3. Features

本系統提供餐廳庫存管理、餐點管理、庫存預測及 AI 輔助查詢等功能，主要功能模組如下。

### 3.1 Authentication & Authorization

提供使用者登入與角色權限管理功能。

- 使用者登入
- JWT 身份驗證
- Admin / User 角色區分
- 根據角色限制功能存取

### 3.2 Inventory Management

提供餐廳食材資料與庫存資訊管理功能。

- 查看食材清單
- 新增、修改、刪除食材
- 設定食材單位
- 設定食材單位成本
- 設定最低庫存量
- 查看目前庫存
- Excel 匯入

### 3.3 Stock Management

提供食材進出貨及庫存異動管理功能。

- 記錄進貨（IN）、出庫（OUT）
- 記錄庫存異動日期
- 根據庫存異動紀錄計算目前庫存
- 查看庫存異動資料

### 3.4 Meal Management

提供餐點及食材使用比例管理功能。

- 查看餐點
- 新增、修改、刪除餐點
- 查看餐點所需食材
- 設定餐點與食材的使用比例
- 執行出餐
- 出餐時依餐點食材比例扣除庫存

### 3.5 Dashboard

提供餐廳目前庫存狀況的視覺化資訊。

- 顯示食材總數
- 顯示目前庫存狀況
- 顯示進貨與出貨統計
- 顯示低庫存食材數量
- 顯示食材庫存圖表

### 3.6 Inventory Forecast

根據歷史庫存使用資料提供未來需求與補貨資訊。

- 設定歷史使用量計算期間
- 設定未來預測期間
- 計算平均每日使用量
- 計算預測需求量
- 計算建議補貨量
- 計算預估補貨成本
- 篩選需要補貨的食材
- 依補貨需求排序

### 3.7 History

提供管理員查詢歷史庫存及匯入記錄的功能。

- 查看歷史庫存異動
- 查看 Excel 匯入記錄
- 查看匯入成功與失敗筆數
- 查看匯入時間及結果

### 3.8 AI Inventory Assistant

提供自然語言的庫存查詢與資訊整理功能。

- 透過自然語言詢問庫存資訊
- 查詢低庫存食材
- 查詢庫存摘要
- 查詢庫存預測
- 依使用者問題選擇適合的 Inventory Tool
- 根據 Tool 回傳資料產生自然語言回答

## 4. Business Rules

### 4.1 使用者與權限

- 使用者登入後才可進行系統操作，Token 有效時間為 2 小時。
- Admin 可管理食材、庫存及餐點資料，並可查看歷史庫存與匯入記錄。
- User 不可新增、修改或刪除食材及餐點資料。
- User 不可查看管理員限定的歷史記錄。

### 4.2 庫存計算

- 每筆庫存異動需記錄食材、異動類型、異動數量及異動日期。
- 異動類型分為 IN 與 OUT。
- IN 代表食材增加庫存，OUT 代表食材減少庫存。
- 目前庫存量 = 所有 IN 數量總和 − 所有 OUT 數量總和。
- 餐點出餐造成的食材扣除，應記錄為 OUT 庫存異動。

### 4.3 餐點管理

- 建立 BOM 前，必須先建立對應的餐點資料。
- BOM 用於定義餐點與食材之間的使用關係及使用數量。
- Admin 可新增、修改及刪除餐點資料與 BOM。

### 4.4 餐點出餐

- 執行出餐時，系統應依 BOM 設定計算各食材所需扣除數量。
- 出餐後，各相關食材應產生對應的 OUT 庫存異動。
- 一次出餐可能同時扣除多項食材庫存。
- 當任一所需食材庫存不足時，不得執行該次出餐；使用者需降低出餐數量至庫存允許範圍後才可執行。
- 一次出餐涉及的庫存異動應具備交易一致性，全部成功或全部失敗。

### 4.5 庫存預測與補貨

- 庫存預測應根據指定歷史期間內的 OUT 庫存異動，計算平均每日使用量。
- 平均每日使用量 = 指定期間內 OUT 數量 ÷ 使用天數。
- 預測需求量 = 平均每日使用量 × 預測天數。
- 建議補貨量 = 預測需求量 + 最低庫存量 − 目前庫存量。
- 若建議補貨量小於 0，則以 0 計算。
- 預估補貨成本 = 建議補貨量 × 食材單位成本。
- 當建議補貨量大於 0 時，該食材視為需要補貨。

### 4.6 Excel 匯入

- Excel 匯入資料需符合系統定義的欄位格式。
- 系統應驗證匯入資料的必要欄位。
- 匯入資料發生格式或資料錯誤時，該筆資料應視為匯入失敗。
- 系統應記錄 Excel 匯入結果。
- 匯入記錄應包含匯入時間及成功、失敗筆數。

### 4.7 AI 庫存助理

- AI 庫存助理負責理解使用者問題及產生自然語言回覆。
- 庫存數量、低庫存資料及預測結果等實際資料，應由後端 Inventory Tools 提供，AI 不得自行推測或產生。
- AI 應根據使用者問題選擇適當的 Inventory Tool。
- 庫存預測結果應由後端既定的庫存預測邏輯計算，不由 AI 自行計算。

## 5. Functional Requirements

### 5.1 Authentication & Authorization

- FR-001 系統應提供使用者登入功能，並驗證帳號與密碼。
- FR-002 系統應透過 JWT Token 驗證使用者身份，並依使用者角色限制功能存取。

### 5.2 Inventory Management

- FR-003 系統應提供食材資料查詢功能。
- FR-004 Admin 應可新增、修改及刪除食材資料。
- FR-005 系統應提供食材單位、單位成本及最低庫存量設定功能。
- FR-006 系統應提供目前庫存量查詢功能。

### 5.3 Stock Management

- FR-007 系統應提供庫存 IN / OUT 異動功能，並記錄食材、異動類型、數量及日期。
- FR-008 系統應提供庫存異動紀錄查詢功能。
- FR-009 系統應根據庫存異動資料提供目前庫存量。

### 5.4 Meal Management

- FR-010 系統應提供餐點資料的查詢及管理功能。
- FR-011 Admin 應可新增、修改及刪除餐點資料。
- FR-012 系統應提供餐點 BOM 管理功能，供 Admin 設定餐點所需食材及使用數量。

### 5.5 Meal Serving

- FR-013 系統應提供餐點出餐功能，使用者可選擇餐點及輸入出餐數量。
- FR-014 系統應依餐點 BOM 計算出餐所需食材，並檢查目前庫存是否足夠。
- FR-015 當庫存不足時，系統應阻止出餐並提供提示。
- FR-016 當出餐成功時，系統應建立對應的 OUT 庫存異動，並確保相關庫存異動一致完成。

### 5.6 Dashboard

- FR-017 系統應提供 Dashboard，呈現食材數量、目前庫存、IN / OUT 統計及低庫存等資訊。
- FR-018 系統應提供庫存相關圖表，以協助使用者了解目前庫存狀況。

### 5.7 Inventory Forecast

- FR-019 系統應提供庫存預測功能，並允許使用者設定歷史使用量及未來預測期間。
- FR-020 系統應根據歷史 OUT 資料計算平均每日使用量及預測需求量。
- FR-021 系統應根據預測需求量、最低庫存量及目前庫存量計算建議補貨量及預估成本。
- FR-022 系統應提供需要補貨的食材篩選及排序功能。

### 5.8 History & Excel Import

- FR-023 Admin 應可查看歷史庫存異動及 Excel 匯入記錄。
- FR-024 Admin 應可匯入 Excel 食材資料，系統並應驗證資料格式及必要欄位。
- FR-025 系統應記錄 Excel 匯入結果，包含匯入時間及成功、失敗筆數。

### 5.9 AI Inventory Assistant

- FR-026 系統應提供自然語言庫存查詢功能，支援低庫存、庫存摘要及庫存預測等資訊查詢。
- FR-027 系統應根據使用者問題選擇適當的 Inventory Tool，並將 Tool 回傳資料提供給 AI 產生自然語言回覆。
- FR-028 AI Tool 發生錯誤時，系統應提供適當的錯誤訊息。

## 6. Non-functional Requirements

### 6.1 Security

- NFR-001 系統應透過 JWT Token 驗證使用者身份，未經身份驗證不得存取受保護 API。
- NFR-002 系統應依使用者角色進行 API 存取權限控管。
- NFR-003 使用者密碼應以雜湊方式儲存，不應以明文保存。
- NFR-004 AI API Key 等敏感資訊不得直接暴露於前端程式碼或版本控制系統。

### 6.2 Data Consistency

- NFR-005 涉及多筆庫存異動的操作應維持資料一致性。
- NFR-006 餐點出餐所產生的多筆庫存異動應以交易方式處理，確保操作全部成功或全部失敗。
- NFR-007 庫存預測結果應由後端既定的計算邏輯產生，以確保計算結果一致且可重現。

### 6.3 Maintainability

- NFR-008 系統應採分層架構設計，將 API Controller、Business Logic 及 AI Tool 等責任分離。
- NFR-009 庫存預測邏輯應與 AI 對話功能分離，以降低功能間的耦合。
- NFR-010 前端應將 API 呼叫、頁面元件及狀態管理分離，以提升程式維護性。

### 6.4 Usability

- NFR-011 系統操作介面應提供清楚的操作結果及錯誤提示。
- NFR-012 系統執行 API 或 AI 請求期間應提供適當的載入狀態。
- NFR-013 Dashboard 應以圖表及摘要資訊呈現重要庫存資訊，降低使用者查詢及判讀成本。

### 6.5 Reliability & Error Handling

- NFR-014 系統應對 API 操作錯誤提供適當的錯誤處理及提示。
- NFR-015 AI Tool 發生錯誤或無法取得資料時，系統應避免產生未經驗證的庫存資訊。
- NFR-016 系統應避免因單一功能操作失敗而造成部分庫存資料更新。

## 7. Scope

### 7.1 In Scope

本次專案主要實作餐廳內部的食材庫存管理及相關輔助功能，包含：

- 使用者登入及 Admin / User 角色權限管理
- 食材資料及庫存資料管理
- 庫存 IN / OUT 異動記錄
- 餐點及 BOM 食材使用比例管理
- 餐點出餐及自動扣除食材庫存
- 庫存 Dashboard 與統計圖表
- 根據歷史使用量進行庫存預測及補貨建議
- Excel 食材資料匯入及匯入記錄
- 歷史庫存異動查詢
- AI 庫存助理，提供自然語言庫存查詢及資訊整理

### 7.2 Out of Scope

本次專案不包含以下功能：

- 不包含使用者帳號建立、修改及刪除功能。
- 不包含實際餐廳 POS 系統串接
- 不包含 ERP、會計或採購系統串接
- 不包含實際自動下單或供應商採購功能
- 不包含多間分店或跨店庫存管理
- 不包含手機原生 App
- 不包含 AI 直接負責庫存數值計算或預測
- 不包含即時供應商價格及市場價格分析
- 不包含正式商業環境的大規模部署及高併發需求

本專案中的庫存預測採用後端既定計算邏輯，AI 主要負責自然語言理解，並透過 Inventory Tools 取得實際資料，不直接產生庫存或補貨數值。
